# 001. Go for every service

**Status:** accepted

## Context
The system is many small network-bound services: an API, consumers that wait on providers (about 50 to 100 ms per call) and schedulers. At the target of 35K dispatch messages per second and 100 ms provider latency, about 3,500 sends are in flight at any moment.

## Decision
Write all services, the CLI tools and the load generator in Go, with one repository, one module and one binary per service.

## Why this is better
- **Cheap concurrency for waiting work.** A worker keeps 150 sends in flight per lane with plain goroutines and a semaphore. No thread pool tuning and no callback code. Kafka batches are processed in parallel with a few lines (`internal/kafkax/batch.go`).
- **Small, fast-starting images.** Static binaries in a distroless image (the router image is 34.8 MB). That matters for autoscaling on lag, because new pods must be ready in seconds.
- **One toolchain end to end.** The services, the generator that tests them and the manifest tests share libraries and types.
- **Pure-Go Kafka client.** `franz-go` avoids cgo, so cross-compiling and container builds stay simple.

## What we give up
- Fewer ready-made stream-processing frameworks than the JVM (no Kafka Streams). We wrote the batch loop, retry routing and coalescing ourselves.
- Error handling is explicit and verbose.

## Evidence
Measured: one API instance accepted 2,000 req/s with p50 0.6 ms (`docs/benchmarks.md`), and the image size above. **Not measured:** a comparison with another language. The advantage over Java, Node or Python is reasoning from the workload, not a benchmark.

## Revisit when
A team without Go experience owns the service, or a need appears for stateful stream processing where Kafka Streams would replace custom code.
