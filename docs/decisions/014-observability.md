# 014. Prometheus, Grafana and OpenTelemetry, with traces carried through Kafka

**Status:** accepted

## Context
A pipeline of asynchronous stages hides problems: a request returns 202 while the real work happens minutes later in other processes.

## Decision
- Every service exposes Prometheus metrics, health and readiness on an admin port, with latency in histograms so any percentile can be charted.
- A lag exporter publishes consumer lag and DLQ size, the signals that matter most for an async system.
- Trace context travels in Kafka headers (and through DynamoDB Streams, stored on the notification record) so one notification is one trace across services.
- Alerts and the dashboard are code: rules in `deploy/prometheus/alerts.yml`, the dashboard generated by `scripts/gen_dashboard.py` and validated by `scripts/check_dashboard.py`.

## Why this is better
- **It measures the right things.** Lag and DLQ growth reveal trouble before users do. Percentiles show tails that averages hide.
- **One trace for one notification.** Debugging "why was this late" no longer means correlating logs by hand. Verified: a single trace contained the API, router and three worker spans.
- **No silent dashboards.** The checker evaluates every panel expression, so a typo in a metric name fails a command instead of showing an empty chart.
- **Reproducible.** Dashboards and alerts live in the repository and are provisioned automatically.

## What we give up
- Cardinality discipline: HTTP metrics label by route pattern, never raw path.
- Tracing every message costs CPU and bytes at high volume. Add sampling before running at peak.
- Some useful metrics are missing (cache invalidation errors, per-lane queue age).

## Evidence
Measured: all 13 scrape targets up, 9 alert rules loaded and validated with `promtool`, 50 dashboard expressions returning data, one cross-service trace in Jaeger.

## Revisit when
Trace volume is a cost problem (sample), or SLOs need burn-rate alerts instead of fixed thresholds.
